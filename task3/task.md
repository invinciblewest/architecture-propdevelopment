# Task3 \- Внешние интеграции: требования

## 1\) Контекст интеграции
Интеграция нужна для предоставления сервисов партнёра через текущее мобильное приложение собственников:
- сервис партнёра: \`SmartHome Partner Platform\`
- внешние сервисы внутри контура партнёра: \`Интеллектуальный домофон\`, \`Интеллектуальный шлагбаум\`
- точка доступа в PropDevelopment: \`tenant-core-app\` 

## 2\) Требования безопасности
1. Все взаимодействия с внешней платформой партнёра должны выполняться по защищённому каналу (TLS).
2. Должна соблюдаться минимизация передаваемых данных: передавать только необходимые атрибуты для выполнения команды и идентификации субъекта/объекта доступа.  
3. Должно вестись аудит\-логирование критичных событий:
    - успешные/неуспешные команды управления (домофон/шлагбаум),
    - попытки доступа,
    - ошибки интеграции,
    - технические корреляционные идентификаторы запросов.
4. Запросы управления доступом должны быть защищены от повторной отправки/подмены (replay/forgery).  
   Конкретный механизм зависит от протокола партнёра.

## 3) Аутентификация и авторизация
### 3.1 Пользователь \-> PropDevelopment (внутренний контур)
- Протокол: `OpenID Connect 1.0` поверх `OAuth 2.0`.
- IdP: `auth-service-1 (Keycloak)`.
- Клиентское приложение получает `ID Token`/`Access Token` (JWT).
- PropDevelopment сервисы валидируют JWT: подпись, `iss`, `aud`, срок действия.

### 3.2 PropDevelopment \-> Партнёрская платформа (межсистемное взаимодействие)
Вариант выбирается по возможностям партнёра, но в требованиях фиксируется как допустимые протоколы:

- Основной вариант (предпочтительный):
    - Протокол: `OAuth 2.0 Client Credentials Grant`.
    - PropDevelopment получает `Access Token` у партнёра и вызывает API партнёра с `Authorization: Bearer <token>`.
- Альтернативы (если OAuth недоступен):
    - `mTLS` (аутентификация по клиентскому сертификату) \+ IP allowlist.
    - HMAC\-подпись запросов (например, `HMAC-SHA256`) \+ `nonce/timestamp`.

### 3.3 Авторизация на уровне домена
- Авторизация пользователя выполняется внутри PropDevelopment до обращения к партнёру:
    - Проверка права собственника на объект доступа (домофон/шлагбаум) по внутренним данным.
- Партнёру передаётся только минимально необходимый контекст:
    - идентификатор объекта (door/gate id),
    - тип команды (open/close),
    - технический идентификатор запроса / корреляция.

## 4) Взаимодействие систем
### 4.1 Общая схема взаимодействия
1. Мобильное приложение (пользователь) вызывает `tenant-core-app`.
2. `tenant-core-app`:
    - валидирует токен пользователя (OIDC),
    - выполняет доменную авторизацию (есть ли право открыть конкретный объект),
    - формирует интеграционный запрос.
3. `tenant-core-app` вызывает API партнёра `SmartHome Partner Platform` (сервис\-to\-сервис):
    - аутентификация \- `OAuth 2.0 Client Credentials` (или mTLS/HMAC по договорённости),
    - обязательные заголовки: `X-Correlation-Id`, `Idempotency-Key` (см\. ниже).
4. Партнёрская платформа выполняет команду во внешних сервисах партнёра (домофон/шлагбаум) и возвращает результат.
5. `tenant-core-app` возвращает пользователю статус операции.

### 4.2 Основные потоки
#### Поток A: Успешная команда «открыть»
1. User \-> `tenant-core-app`: `POST /access/open` с параметрами объекта.
2. `tenant-core-app` проверяет права (внутренний ownership check).
3. `tenant-core-app` \-> Partner API: `POST /commands/open` с `X-Correlation-Id` и `Idempotency-Key`.
4. Partner API \-> внешние сервисы партнёра: выполнение.
5. Ответ Partner API: `200 OK` (или `202 Accepted`, если асинхронно).
6. Ответ пользователю: успех.

#### Поток B: Асинхронное выполнение (если у партнёра 202)
- При `202 Accepted` партнёр возвращает `operationId`.
- `tenant-core-app` опрашивает статус `GET /operations/{operationId}` или принимает callback/webhook (если партнёр поддерживает).
- Требование: все статусы опроса/колбэков коррелируются через `X-Correlation-Id` и/или `operationId`.

### 4.3 Таймауты, ретраи, обработка ошибок
- Таймауты:
    - connect timeout: 1\–3s,
    - read timeout: 3\–10s (зависит от SLA партнёра),
    - общий deadline на команду \- фиксируется (например, 10s) и возвращается пользователю с понятным статусом.
- Ретраи:
    - ретраи допускаются только для безопасных ошибок: сетевые ошибки, `503`, `504`, `429`.
    - при ретраях обязательно сохранять `Idempotency-Key`, чтобы исключить повторное открытие.
- Коды ошибок и поведение:
    - `401/403` от партнёра: ошибка аутентификации/авторизации интеграции \- алертинг, без ретраев.
    - `400` \- ошибка запроса \- без ретраев, логирование и корректировка маппинга/контракта.
    - `409` \- конфликт/дубликат по идемпотентности \- трактовать как повтор предыдущего запроса (возвращать ранее известный результат, если партнёр так умеет).
    - `5xx` \- временная проблема \- ретраи по политике, далее деградация.

### 4.4 Идемпотентность и корреляция
- Корреляция:
    - `X-Correlation-Id` генерируется при входящем запросе от клиента (или принимается, если уже задан) и прокидывается во все внутренние логи/вызовы к партнёру.
- Идемпотентность:
    - Для операций управления доступом обязателен `Idempotency-Key`.
    - Формат: UUID (генерируется на стороне `tenant-core-app`) на каждую команду пользователя.
    - Требование: повторный запрос с тем же `Idempotency-Key` должен приводить к тому же результату без повторного фактического действия (по возможности, через поддержку партнёром; иначе \- хранить результат у себя на время окна идемпотентности).
- Защита от replay:
    - В дополнение к `Idempotency-Key` использовать `timestamp/nonce` или подпись (если требует партнёр).

### 4.5 Контракты и версионирование
- Интеграционный API должен быть версионирован (`/v1/...`).
- Изменения контракта: backward compatible по умолчанию, с согласованным периодом деприкации.
